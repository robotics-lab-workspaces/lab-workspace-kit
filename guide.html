今の稼働状況

Ubuntuの端末で、クローンした lab-workspace-kit フォルダーから実行します。

Ubuntuホストキットのフォルダーで
./labctl doctor

STATUS 欄の Up は稼働中、Exited は停止中です。ポートと、稼働中のCPU・メモリの使用量も表示されます。

閉じる・止める・開き直す

  • コンテナを停止

    Ubuntuホスト
    sudo docker stop mujina-gpu0-student01

    自分のコンテナ名を指定します。中の学習やTensorBoardも止まるので、先に作業を保存します。

  • 開き直す

    Ubuntuホスト
    ~/agent-lab/student-lab student01 --gpu 0

    同じ作業名とGPU指定なら、同じコンテナ・追加パッケージ・データに戻ります。停止中なら起動してから入ります。

  • 端末だけ閉じる

    コンテナ内
    exit

    Ubuntuホストの行頭に戻ります。コンテナは起動したままです。

  • 処理を止める

    処理が動いている端末
    Ctrl + C

    その端末の前面で動いている学習・再生・TensorBoardだけが止まります。

Ubuntuホスト
ログインした直後のシェル。行頭は labadmin@…$ など
コンテナ内
行頭が lab@mujina-gpu0-student01:/workspace$ のように表示されます

student01 と gpu0 は例です。自分の作業名とGPU指定に合わせた名前はコンテナ名の表で確認できます。コンテナを消して作り直す docker rm は非常時の手順でだけ使います。

全体の流れ

コンテナに入る

Ubuntuデスクトップで Ctrl+Alt+T を押してターミナルを開き、冒頭の開き直すのコマンドを実行します。初回は環境が作られ、2回目以降は同じコンテナに戻ります。行頭が lab@mujina-… に変われば中に入れています。

コマンドは「コピー」を押し、ターミナルをクリックして Ctrl+Shift+V で貼り付け、Enter で実行します。sudo がパスワードを求めたときは、文字が表示されなくてもそのまま入力して Enter を押します。

GPU指定とコンテナ名

モード入るコマンドの末尾コンテナ名（停止のときに使う）
GPU 0--gpu 0mujina-gpu0-student01
GPU 1--gpu 1mujina-gpu1-student01
GPU 2枚とも--gpu allmujina-gpuall-student01
通常版（GPUなし）何も付けないmujina-student-student01

MuJinaの学習と再生はGPU版で行います。モードごとに別のコンテナになりますが、/workspace の中身は共通です。

フォルダーの場所を確かめる

コンテナ内の /workspace は、Ubuntu側の ~/agent-lab/students/作業名/workspace/ と同じ中身です。学習プロジェクトは /workspace/mujina_isaac_lab にあります。

pwd で今いる場所、ls でその中身が表示されます。cd /workspace で作業フォルダーに移動します。~ は自分のホームフォルダーの略です。

コンテナを再起動して入り直す

停止と同じく、中の学習・シミュレーター・TensorBoardは終了します。追加したパッケージ、作業ファイル、設定は残ります。

UbuntuホストGPU 0版を再起動して入る
sudo docker restart mujina-gpu0-student01 &&
~/agent-lab/student-lab student01 --gpu 0

学習

最初は、ロボット8体（--num_envs 8）・1反復（--max_iterations 1）の短い設定で、GPUでの計算、モデルの読み込み、保存が通ることを確かめます。

コンテナ内短い動作確認
mujina-isaac train --task Isaac-Velocity-Rough-Mujina-v0 \
  --num_envs 8 --max_iterations 1 --logger tensorboard --headless

結果は /workspace/mujina_isaac_lab/logs/rsl_rl/ に保存されます。学習中はこの端末を開いたままにし、ほかの作業は2つ目のターミナルで行います。

--headless は画面を出さない指定です。画面を見ながら試すときは、Ubuntuデスクトップから入ってこの指定を外します。1反復の結果は保存と読み込みの確認用で、歩く様子を見るには十分に学習したチェックポイント（学習途中のモデルを保存したファイル）が必要です。

再生

ウィンドウはUbuntuデスクトップに出ます。デスクトップのターミナルから入ったGPUコンテナで実行し、終わるときはその端末で Ctrl+C を押します。

公式モデルを再生する

コンテナ内同梱の歩行モデルを画面付きで再生
bash /workspace/policies/play-mujina.sh

RT公式の学習済み歩行ポリシー（動かし方を決めるモデル）を読み込み、Isaac Sim（ロボットのシミュレーター）でMuJina 1体に前進を指示します。スクリプトが見つからないときは、同じ作業名で入り直します。

自分の .pt を再生する

同じコンテナで学習したRough-MuJinaの結果から最新のチェックポイントを探し、再生スクリプトの末尾に渡します。コピーして、まとめて貼り付けます。

コンテナ内自分のモデルを画面付きで再生
logs=/workspace/mujina_isaac_lab/logs/rsl_rl/mujina_rough
checkpoint=$(find "$logs" -type f -name 'model_*.pt' 2>/dev/null | sort -V | tail -n 1)
if [ -n "$checkpoint" ]; then
  bash /workspace/policies/play-mujina.sh "$checkpoint"
else
  printf '%s\n' 'この環境には学習結果がありません。'
fi

特定の回を使うときは、bash /workspace/policies/play-mujina.sh の後ろにその .pt の絶対パスを書きます。自分の学習回は ls /workspace/mujina_isaac_lab/logs/rsl_rl/mujina_rough/ で一覧できます。

再生でファイルのエラーが出たら

cannot execute binary file：.pt を直接実行しようとしています。bash の直後が play-mujina.sh のパスになっているか確かめ、上のコマンドをまとめて貼り直します。

No such file or directory：指定した場所にファイルがありません。作業名が合っているか、/workspace に目的のファイルがあるかを確かめます。

モデルの表示や動作確認だけしたいとき
コンテナ内Isaac SimでMuJinaを表示（プレビュー）
mujina-isaac preview

プレビューは1体のモデルと物理を、入力ゼロのまま確かめるモードです。歩きません。

コンテナ内MuJina ROSをMuJoCoで表示
mujina-ros-sim
コンテナ内画面なしでIsaacの動作確認（3ステップで終了）
mujina-isaac preview --headless --steps 3

TensorBoard

学習の経過をブラウザーのグラフで見るツールです。

  1. 学習中の端末はそのままにして2つ目のターミナルを開き、同じ作業名・GPU指定で入ります。入るときに表示されるUbuntu側のURL（http://localhost:32771 など）を控えます。
  2. コンテナ内で次を実行します。グラフを見ている間、この端末は開いたままにします。
    コンテナ内既定の学習ログを読む
    mujina-tensorboard
  3. 控えたURLをUbuntuのブラウザーで開きます。

URLの番号（ポート）はDockerが空きを選ぶため、コンテナごとに違い、停止・再開で変わることもあります。今の番号は稼働状況の PORTS 欄で確認できます。コンテナ内の番号は常に 6006 で、TensorBoardは1コンテナにつき1つです。TensorFlowが入っていないという通知は、起動できていれば気にしなくて構いません。

Macから開く

32771 をUbuntuで表示された番号に、labadmin と lab-host.example.org を管理者に指定された値に置き換えてMacで実行し、そのままMacのブラウザーで http://localhost:16006 を開きます。

MacのターミナルSSH転送（Ubuntuのポートを手元に中継）
ssh -N -L 16006:localhost:32771 labadmin@lab-host.example.org

この転送で見られるのはTensorBoardだけです。Isaac SimのウィンドウはUbuntuデスクトップに出ます。Dockerのポート公開の仕様

状況を直接確認

ふだんは冒頭の稼働状況の確認コマンドで足ります。1項目ずつ確かめたいときは、Ubuntuホストで次を実行します。

Ubuntuホスト起動中のコンテナだけ
sudo docker ps
Ubuntuホスト停止中のコンテナも含める
sudo docker ps -a
Ubuntuホスト今のCPU・メモリ使用量（1回分）
sudo docker stats --no-stream
Ubuntuホストマシン全体のGPUの使用状況
nvidia-smi

stats のCPU欄は、複数の論理CPUを使うと100%を超えます。キット自体の点検結果を端末で読むなら、キットのフォルダーで ./labctl doctor を実行します。

列を絞って見やすくする
Ubuntuホスト名前・状態・ポートと、使用量だけ
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
sudo docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}'
自分のコンテナに割り当てられたGPUを確認する
Ubuntuホストマシン全体と、コンテナから見えるGPU
nvidia-smi --query-gpu=index,uuid,name,memory.total --format=csv
sudo docker exec mujina-gpu0-student01 \
  nvidia-smi --query-gpu=index,uuid,name,memory.total --format=csv

2つ目の一覧が、そのコンテナから使えるGPUです。ホストでGPU 1を渡しても、コンテナ内ではGPU 0と表示されることがあるので、両方の uuid を見比べます。通常版にはGPUの割り当てがありません。

CPUとRAMの上限を確認する
Ubuntuホストマシン全体の容量と、コンテナの上限
nproc
free -h
sudo docker exec mujina-gpu0-student01 sh -c '
  printf "CPU quota: "; cat /sys/fs/cgroup/cpu.max
  printf "CPU IDs: "; cat /sys/fs/cgroup/cpuset.cpus.effective
  printf "Memory bytes: "; cat /sys/fs/cgroup/memory.max
'

CPU quota が max なら、CPU時間の上限はありません。CPU IDs は使える論理CPUの番号、Memory bytes はRAMの上限です。既定の上限は通常版24 GiB、GPU版64 GiBです。

セットアップ・復旧・バックアップ

マシンを最初に準備するときと、環境が壊れたときに使います。ここのコマンドはすべてUbuntuホストで実行します。

新規セットアップ

Ubuntu 24.04に、Docker Engine、Python 3.12以上、Gitを用意しておきます。GPU版の条件はREADMEにあります。

Ubuntuホスト取得して対話メニューを開く
git clone https://github.com/robotics-lab-workspaces/lab-workspace-kit.git &&
cd lab-workspace-kit &&
./labctl

メニューで「セットアップ」を選びます。通常版だけなら ./labctl setup でも作れます。

GPU版を作る・プロキシのあるネットワークで作る

GPU版は、NVIDIAの条件を読み、同意する場合に実行します。初回のビルドには十分な空きディスクと時間が必要です。

Ubuntuホストキットのフォルダーで・GPU版
./labctl --accept-isaac-eula setup --gpu

プロキシが必要なネットワークでは、実行前にシェルの http_proxy と https_proxy を設定します。Docker Hubに届かない場合は、用意済みのUbuntu 24.04イメージを LAB_KIT_UBUNTU_BASE=local-ubuntu:24.04 ./labctl setup のように指定できます。

復旧

共通の起動ファイルやコンテナを失っても、~/agent-lab/students/ に作業データが残っていれば、同じ作業名につなぎ直せます。そのあとは、いつもの student-lab で入ります。

Ubuntuホストキットのフォルダーで・残っている作業データから復旧
./labctl repair
保存場所残るもの
students/<作業名>/workspaceコード・学習ログ・チェックポイント。通常版とGPU版で共通
同じ作業名の state / state-gpu*各モードのコンテナのホーム（/home/lab）。設定・認証など
コンテナ本体手動で apt などで追加したもの。本体を失ったら、作業メモをもとに入れ直す
保存場所が違う・GPU環境を作り直す場合

別の保存場所では ./labctl --root /path/to/agent-lab repair を使います。GPU環境を作り直すときに同意済みの設定が残っていなければ、条件を確認してから ./labctl --accept-isaac-eula repair を使います。別の名前空間で使っていた環境には、同じ --namespace を指定します。オプションは repair より前に書きます。

イメージの選び直しなど、細かい条件はREADMEの復旧手順にあります。

まっさらな標準環境で試したい

コンテナは消さずに、未使用の作業名で入ります。元の環境には、元の作業名で戻れます。

Ubuntuホスト別の新しい作業名を作る
~/agent-lab/student-lab student01-clean --gpu 0
非常時：同じ作業名のままコンテナ本体を作り直す（docker rm）

コンテナが壊れて入れないときだけ使います。コンテナに直接入れた apt パッケージと、/workspace・/home/lab の外に置いたファイルは消えます。実行前に sudo docker ps -a で自分のコンテナ名を確かめます。

Ubuntuホスト自分のGPU 0版だけを作り直す
sudo docker stop mujina-gpu0-student01 &&
sudo docker rm mujina-gpu0-student01 &&
~/agent-lab/student-lab student01 --gpu 0

/workspace のコード・学習ログと、同じモードの /home/lab の設定・認証はUbuntu側に保存されているので、そのまま引き継がれます。

バックアップ

Ubuntuホストキットのフォルダーで・学生の作業データをまとめて保存
./labctl backup --output /mnt/backup/lab-students.tar.gz

認証ファイルが含まれることがあります。ファイルの権限は 0600（本人だけが読み書きできる設定）にし、配布先やGitには置きません。学習中のファイルまで正確に残したいときは、作業を保存して停止してから取り、外部ストレージへ移します。

バックアップから空の保存先へ復元する

同じマシンに既存の環境があるときは、例のように名前空間を分けます。

Ubuntuホストキットのフォルダーで・アーカイブから復元
./labctl --root "$HOME/recovered-lab" --namespace recovered repair --archive /mnt/backup/lab-students.tar.gz

守る範囲

編集するのは自分の /workspace の中だけです。停止や作り直しは、sudo docker ps -a で自分のコンテナ名を確かめてから指定します。

ほかの人の環境
~/agent-lab/students/他の作業名/ のコード・学習ログ・認証と、ほかの人のコンテナには触りません。停止や削除も本人に任せます。
共通の起動設定
~/agent-lab/student-lab、~/agent-lab/compose*.yaml、~/agent-lab/mujina-image/ は全員の環境に関わります。実験コードは、自分の作業フォルダーにあるコピーを編集します。
UbuntuとDockerの管理領域
/etc/docker/、/etc/cdi/、/var/lib/docker/、GPUドライバー、ネットワーク設定は管理担当者が扱います。Docker全体を消す・止めるコマンドや docker system prune は使いません。
実機と認証情報
シミュレーションの作業中は、実機のCAN・制御ノード・実機接続に触りません。SSH鍵、パスワード、APIキー、X11認証は作業ログやGitに貼りません。

共通設定の問題に気づいたら、実行したコマンド、エラー、自分のコンテナ名を管理担当者に伝えます。

トラブル

command not found と出る

行頭を見て、どちらのシェルにいるかを確かめます。mujina-isaac などはGPU版のコンテナ内、student-lab や sudo docker はUbuntuホストで実行します。

Isaacのウィンドウが出ない

Ubuntuデスクトップのターミナルから student-lab で入り直し、mujina-isaac preview を実行します。初回は描画キャッシュの準備に時間がかかります。

ウィンドウは出たがロボットが歩かない

プレビューは入力ゼロで表示するだけです。歩かせるには、学習済みの .pt を使う再生を実行します。

TensorBoardが開かない、グラフが空

「6006 already in use」と出るのは、同じコンテナでTensorBoardがすでに動いているためです。入るときに表示されたUbuntu側のURLを開けば、そのまま使えます。

開かないときは、同じコンテナで mujina-tensorboard が動いているか、URLが今回表示されたものかを確かめます。画面は開くのにグラフが空なら、/workspace/mujina_isaac_lab/logs に学習の記録ファイルがあるかを見ます。

CUDAエラーや Resource temporarily unavailable が出る

まず、コンテナ内でGPUが見えているかを確かめます。pids.events の max の数が増え続けるなら、プロセス・スレッド数の上限（GPU版は2048）に達しています。Isaacの詳しいログは ~/.local/share/mujina-isaac/logs/ にあります。

コンテナ内GPUとプロセス数の上限
nvidia-smi -L
cat /sys/fs/cgroup/pids.max /sys/fs/cgroup/pids.events

作業メモは自分の /workspace/WORKLOG.md に残します。共有ルールは /workspace/AGENTS.md、環境の再ビルド手順は ~/agent-lab/mujina-image/README.md にあります。

補足：Ubuntuに直接入れたIsaac Sim

コンテナを使わずにIsaac Sim単体を開くときは、インストール方法に合うほうを使います。Isaac LabでMuJinaを動かす場合は、MuJinaプロジェクトの train.py または play.py から始めます。

Ubuntuホスト配布版を展開したフォルダーで
./isaac-sim.sh
Ubuntuホストpip版を入れたPython環境で
isaacsim
